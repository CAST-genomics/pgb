Frequency color ramps

PGB has five color ramps that turn a frequency between 0 and 1 into a node color. This page draws each one as the 3D graph draws it, on the heatmap scene’s background, and says how to call it.

The five ramps

Three are sequential: they run from light to dark, so a darker node means a higher frequency. Two are diverging: blue at 0%, a neutral gray at 50% and red at 100%, so a node’s hue says which side of one half it falls on.

Only blues is a single hue. ylGnBu and ylOrRd are still sequential, light to dark, but they pass through three neighboring hues on the way.

HeatmapLook uses blues. It used the continuous diverging ramp until November 2026, when the request came to show frequency with one color rather than two opposed ones.

The three sequential ramps are ColorBrewer 2.0 schemes, by Brewer, Harrower and Sheesley, and live in src/utils/color/color-ramps.js. The two diverging ramps were designed for PGB and live in src/utils/color/tufteHeatmapColors.js; notes/ui/color/heatmap-color-notes.md gives the reasoning behind them. The midpoint was darkened from #f6f6f6 to #cccccc for legibility.

How dark each one gets

Lightness is what the eye reads as “more”. Figure 2 plots each ramp’s OKLab lightness, from 0 for black to 1 for white, against frequency.

The sequential ramps fall all the way, so lightness alone orders the nodes, and that order survives colorblindness and grayscale. blues spans the widest range, from 0.99 to 0.32. ylOrRd stops at 0.48, so its high end is the least dark of the three.

The diverging ramps are as dark at 0% as at 100%, and lightest in the middle. Lightness tells a reader how far a frequency is from one half, and only hue tells them in which direction.

Against the background

All three sequential ramps start almost at the background’s color. On the ivory scene, nodes with low frequencies fade out of the graph.

Diverging, continuous #2f76b7 44.8 0% 0.55
Diverging, five steps #2f76b7 44.8 0% 0.55
The difference is ΔE in OKLab, scaled by 100. About 2 is the smallest difference most people notice side by side. 10 is the threshold used here for “clearly visible”, which is a judgment, not a standard.

With blues, a node at 0% differs from the background by 1.1, which is invisible, and nodes stay faint up to about 24%. The diverging ramps never had this problem, because both ends are saturated colors.

If faint nodes are a problem in the app, start the ramp partway in, so that 0% maps to a visible blue:

blues.color(0.25 + 0.75 * frequency)

This keeps the same order and gives up a quarter of the ramp’s range. The other choice is to accept the fading: a node near 0% is carried by almost no one in the selected population, and it is fair for it to recede.

Using a ramp in a Look

Every ramp has a call that takes a frequency t and returns a THREE.Color. Each call clamps t to between 0 and 1. The ramps’ stops are sRGB, and every call tags them as sRGB, so Three.js converts them to its linear working space, and the node shows the hex value in Figure 1.

Never hand ramp.rgb(t) to setRGB as it is. The values are 0 to 255 instead of 0 to 1, and untagged values are taken as linear, so the color comes out wrong twice.

HeatmapLook colors each node with:

const color = blues.color(rawFrequency ?? 0)

The ?? 0 matters. A node with no frequency for the selected population has undefined, and a ColorBrewer ramp given undefined throws, which would stop the remaining nodes from being colored. With the guard, such a node is drawn as 0%.

frequencyToColorDiscrete returns one of five shared THREE.Color instances, so a Look must copy it and never change it in place. HeatmapLook already copies.

To change ramps, change the one call in HeatmapLook.handleSelectionEvent. To let the user choose, make the ramp a parameter of HeatmapLook, rather than choosing it outside the Look.

PGB has categorical palettes too, rubinColors and the Apple Crayon colors in src/utils/color/color.js. They name colors and order nothing, so they are not shown here.
